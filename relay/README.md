# TDX 中繼服務

App 的交通分頁原本直接打交通部的 TDX，金鑰用 `--dart-define` 編進 APK。
自己一個人用沒問題，**公開發布會壞**。這個服務就是為了那件事。

## 為什麼需要它：問題不是保密，是配額

`--dart-define` 的值會編進 APK，反編譯挖得到 —— 這件事現在就成立。
但那不是重點，因為 TDX 免費金鑰被挖走最壞就是配額被吃掉。

真正會壞的是：**TDX 的速率限制綁在金鑰上，不是綁在使用者上。**

五百個學生共用同一把金鑰，每人開著交通頁每 30 秒打 3 個請求，加起來
每秒 50 個請求打在同一把金鑰上。不用等到有人反編譯，第一天就全部 429。

## 為什麼它可以很便宜

**那五個站的資料，對所有使用者都是同一份。**

這是整件事的關鍵，不是順便的最佳化。服務抓一次、快取起來，不管有 5 個
還是 5000 個使用者來要都回同一份 —— **打到 TDX 的請求量跟使用者數量
完全無關**，穩定狀態是 2.5 次／分鐘（怎麼算出來的見下面那節），
比一個人直接用還少。

所以 Cloudflare Workers 的免費額度（每天十萬次請求）綽綽有餘。

## 順帶解決的三件事

- **使用者幾乎不會再撞到 429**，因為他們拿到的是快取。（「幾乎」是後來
  才學到的：快取 TTL 如果跟重整頻率一樣長，等於每次都沒中，這個服務就
  一次都沒替 TDX 擋到。見〈免費金鑰每分鐘只有 5 個請求〉。）
- **App 端不再需要金鑰**，`--dart-define` 那套可以拿掉，也不會再有
  「漏帶參數就安靜變成『交通資訊還沒開通』」這個坑。
- 交通那半邊本來就沒有個資（不用登入、站是寫死的），所以這個服務看得到的
  只有「有人打開了交通頁」。**沒有任何值得保護的東西經過它** ——
  學校的帳密走的是完全不同的路，一個位元組都不會碰到這裡。

## 部署

需要一個 Cloudflare 帳號（免費，Workers 免費方案不用信用卡）。

```bash
cd relay
npx wrangler login
npx wrangler secret put TDX_CLIENT_ID
npx wrangler secret put TDX_CLIENT_SECRET
npx wrangler deploy
```

`wrangler deploy` 會印出網址，像 `https://ntou-tdx-relay.<你的帳號>.workers.dev`。

確認它活著：

```bash
curl https://ntou-tdx-relay.<你的帳號>.workers.dev/health
```

**金鑰是用 `wrangler secret put` 放的，不在 `wrangler.toml` 裡，也不在
任何進版控的檔案裡。** 這才是跟 `--dart-define` 真正的差別 ——
那個會編進 APK，這個不會。

## 讓 App 走中繼

把網址填進 `app/assets/transit.json` 的 `relay_base_url`：

```json
"relay_base_url": "https://ntou-tdx-relay.你的帳號.workers.dev/"
```

填了之後 build 就**不需要任何金鑰**：

```bash
cd app && flutter build apk --release --target-platform android-arm64
```

留空的話行為完全照舊（直接打 TDX，需要金鑰）。想臨時指到別的中繼可以用
`--dart-define=TDX_RELAY_URL=...` 蓋過設定檔。

## `/batch`：一次問好幾個

桌面小組件每次更新要三份資料（基隆市公車、國道客運、台鐵）。分開打就是
**三個 Worker 請求** —— 而小組件跟 App 不一樣，它裝了就一直在背景更新，
跟使用者有沒有在看無關。五百個人各裝一個、每 30 分鐘更新一次，一天就是
七萬多個請求，逼近免費方案每天十萬的上限。併成一個就降到兩萬四。

```
GET /batch?r=<路徑?查詢>&r=<路徑?查詢>
```

每個 `r` 是 URL 編碼過的「路徑 + 查詢字串」，一次最多 6 個。回應：

```json
{ "results": [ { "path": "...", "status": 200, "cache": "HIT", "data": { } } ] }
```

順序跟 `r` 一致，**一個失敗不會拖垮整批**（`status` 不是 200、`data` 是
null）—— 跟 App 裡「一站失敗不影響其他站」同一個道理：台鐵掛了公車還是要能看。

**這不會增加打到 TDX 的量**，但也**不會減少**。每一份還是走跟單獨查詢
完全相同的快取鍵，所以兩條路共用同一份快取；上游請求數只由 TTL 和
「多久沒中一次」決定，跟客戶端怎麼包無關。這裡省的是 Worker 自己的請求數
（Cloudflare 每天十萬那個額度），不是 TDX 每分鐘五次那個額度。

**而且一批三個會一次吃掉三個上游額度**（`serveBatch` 用 `Promise.all`
平行走 `serveOne`）。所以在 `UPSTREAM_PER_MINUTE` 的眼裡，一個 `/batch`
是這個服務單次最大的消費者 —— 同一分鐘內第二批就會開始吃備胎。

整批的 `max-age` 取最短的那個，而且**只要有一個失敗就整批不快取** ——
把一份缺了公車的結果快取起來，等於讓後面每個人都看到同一個破洞。

> App 端目前還沒走這條，交通分頁和小組件都還是分開打三個。要接的話得改
> `TransitRepository.boards()` 把三個查詢合起來送。

## 設計上的兩個決定

**做成透明代理**（`/v2/Bus/...` 原樣轉發）而不是自訂端點。這樣 App 那邊
只要換 base URL、拿掉 authorization header，所有解析邏輯一行都不用動，
中繼也不用複製一份「有哪些站、哪些路線」的知識 —— 那份知識已經在
`transit.json` 裡了，抄第二份就是等著它們哪天不一致。

**路徑白名單是安全邊界，不是方便性設定。** 沒有它的話這就是一個掛著你的
金鑰的開放代理，任何人都能拿去打 TDX 的任意端點，配額照樣被吃光 ——
那等於什麼都沒解決。查詢參數也是白名單過濾後**重組**的，不是把
`?` 後面原樣接上去：原樣接的話，多帶一個無意義的參數就會產生一個新的
快取鍵，快取形同虛設，而快取正是這整個服務存在的理由。

## 免費金鑰每分鐘只有 5 個請求

**這是這個服務所有數字的來源。** 2026-09-05 直接打 TDX 看回應 header：

```
X-RateLimit-Limit-Minute = 5
X-RateLimit-Remaining-Minute = 4
RateLimit-Reset = 48
```

每分鐘 5 個，不是常見的每秒幾十個。這個數字小到會改變整個設計。

**原本的設定必然爆掉**：App 每 30 秒問三個到站端點（基隆市公車、國道客運、
台鐵看板），而那三個的快取剛好也是 30 秒 —— 等於每次都沒中，穩定
6 次／分鐘。**光是把交通分頁開著就一定超過**，每分鐘至少一個請求被回 429，
畫面上就是「交通資料服務忙碌中」。點進一條沒看過的路線更慘：那份站序
一份備胎都沒有，整頁空白。

兩個地方對這件事負責：

- **快取 TTL 照額度訂**（下表），穩定狀態壓到 2.5 次／分鐘
- **`UPSTREAM_PER_MINUTE`**：額度用完就寧可給備胎，不要打過去。重點不是
  省那一次失敗，是**把額度留給沒有備胎可給的請求** —— 到站資料手上一定有
  舊的一份，第一次點進的那條路線的站序是真的沒有

（計數在 isolate 記憶體裡，多個 isolate 會各算各的。它是減壓閥不是保證，
真的超過還有 STALE 那條路接著。）

## 快取多久

| 資料 | 秒 | 為什麼 |
|---|---|---|
| 公車到站、公車位置 | 60 | **被上面那個 5 次／分鐘決定的。** 資料在 TDX 端每 30 秒換一次（台鐵回應外層自己帶著 `UpdateInterval: 30`），所以 30 秒的快取不會抓到更舊的東西 —— 但一分鐘打 6 次就是必爆 |
| 台鐵看板 | 120 | 它現在只拿來補誤點分鐘數（班次本身走時刻表），誤點兩分鐘更新一次夠了 |
| 路線站序、路線、站牌 | 21600（6 小時） | 一天才變一次，而且回應最大（103 兩條子路線就 132 個站牌），快取久一點省最多 |
| 台鐵每日時刻表 | 3600 | 今天的時刻表本來就不會變 |
| 台鐵車站清單 | 86400 | 一天 |

回應會帶一個 `x-relay-cache` 的 header：`HIT`（命中快取）、`MISS`（去問了
TDX）、**`STALE`（TDX 掛了或擋我們，給的是備胎）**。除錯的時候看它最快。

備胎是另外存的第二份，放十分鐘。為什麼需要它：邊緣快取過期之後那筆就不見了，
而「過期」跟「沒用」是兩回事 —— TDX 擋人的時候（開發過程撞過好幾次 429），
一份三分鐘前的公車時間遠比一個錯誤訊息有用。十分鐘之後就寧可報錯，
太舊的資料比沒有資料更危險。

## 之後可能要處理的

- **濫用。** 路徑白名單擋掉了任意端點，但在允許的端點裡有人可以一直變換
  `$filter` 來繞過快取、把上游請求打出去。真的發生的話，Cloudflare 的
  rate limiting 規則是第一步；再不行就把透明代理換成固定端點
  （`/board`、`/route/103`），完全不接受自由查詢。
- **token 存在 isolate 記憶體裡**，isolate 換掉就重換一張。目前沒問題，
  因為大部分請求命中快取、根本不需要 token。量大到會困擾的話再改用 KV。
